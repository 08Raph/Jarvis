## 2. Rules for every test below

- Use a throw-away profile: add `--data-dir C:\jarvis-test\data` before the subcommand. Never test on your real data folder.
- Write down the exact command, the exit code (`$LASTEXITCODE` straight after the command), the date and the Windows build.
- Any unexpected behaviour is a finding: stop, keep the files, do not retry silently, report it.
- **Diagnostics without secrets.** Share `jarvis diagnostics` output, `selftest.json` and `desktop audit` after reading them yourself. They are designed to hold no prompts, replies, conversation text or keys, but logs can still contain folder names or your user name. Never share `memory.sqlite`, `settings.json`, a `.pem`, a crash log you have not read, or a screenshot showing private windows. For "does it leak?" checks, type an obviously fake secret (for example `FAKE-KEY-0000`), never a real one.
- Do not paste prompts or replies from real conversations into a report; describe them ("a 3-paragraph request: reply was cut off after paragraph 1").

## 4. What the skipped tests are

- **Opt-in real model** (4 tests in 4 files; `JARVIS_REAL_MODEL_TEST=1` + `JARVIS_REAL_MODEL_PATH`): tool-call parsing, planning, new tools, and `test_p73_inference_behaviour.RealRuntime` (load a genuine GGUF through llama-cpp-python, reply, stream, stop, reuse; set `JARVIS_REAL_MODEL_REPORT=file.json` to record model, runtime version and timings). They stay skipped everywhere until you run them in part 4 of the checklist. **These opt-in tests (the `RealRuntime` test and its three siblings) have never been run with real weights.** The real model WAS exercised by older CI workflows (`docs/VERIFICATION_LEDGER.md`); what has not happened is a real run of THESE tests or of the current code (exact steps, prerequisite check and expected report: `docs/REAL_INFERENCE_CHECKLIST.md`): the authoring sandbox has no llama-cpp-python (PyPI is blocked) and cannot reach a model host (huggingface.co is blocked), and the only CI path (a manual run of windows-ci with the consent value, about 1.28 GB download) was not used. Two of the older opt-in tests built `GGUFEngine` from the .gguf FILE instead of a model folder and would have failed on first real use; they now use `engine_for_gguf_file` (tests/p10_common.py).
- **Qt** (`JARVIS_QT_TEST=1`): needs PySide6.
- **Everything else skipped.** Windows skips more than Linux (108 vs 75). The reasons visible in the CI annotations (which list only the first 40 skips per job) are: POSIX shell-script stand-ins (p65), no genuine plugin sandbox on win32, `PyYAML is not installed`, the POSIX-only process-group kill test (Windows); on Linux, the plugin sandbox, because `unshare` is refused on the hosted runner. The rest of the 183 are not itemised anywhere I can read. **`PyYAML is not installed` matters:** the tests that parse `windows-ci.yml` (shape and timeout nesting) are skipped on Windows CI, and most likely on Linux CI too (its install step has no PyYAML; its skip list is cut off before that point), so those workflow-shape checks have only run on the author's machine.

## 5. Known unexplained items

- **Intermittent P17 / microphone tests.** Established: `test_no_microphone_device` (and five similar checks) asserted "no voice thread" the instant the state flipped to `Unavailable`/`Off`, but the worker thread returns a moment later; they now wait, bounded and by condition, and look only at threads of their own controller. Not established: why three gated P17 tests failed once on Windows CI (run 40795644979). Those were plain `ERROR`s from the temp-folder cleanup (`PermissionError` on `memory.sqlite`) with the test bodies passing; the controller's 2 s shutdown had left a task running and its database open. Why a task outlived 2 s on that runner was not captured (the full log is not readable from here) and has not been reproduced. The Rig cleanup now waits for the task (bounded) or fails naming it. The same runner showed a `chat` task outliving a 3 s shutdown in a p10 test, so a transient slow period on that runner is the likeliest cause, but that is an inference, not a measurement. **Re-investigated (evidence recovered from the run's check-run annotations):** that run had FOUR `PermissionError [WinError 32]` cleanup errors on `memory.sqlite` (the three P17 tests above plus `test_p10_controller.ShutdownTests.test_shutdown_stops_a_running_reply_and_blocks_new_work`, whose own assertion `shutdown(3.0) == {'still_running': []}` also failed with `['chat']`), and a p63 crash-detection test failed in the same run. Measured: the Windows unit-test step took 661 s in that run against 268-359 s in each of the six other Windows runs inspected, so the runner WAS about twice as slow, and slow tests (4-10 s) were listed. Not reproduced: 16 busy processes on 2 cores did not stretch the p10 shutdown beyond 0.17 s (0.13 s idle), so CPU contention alone does not explain it; slow disk or antivirus I/O on the runner is a guess, not evidence. There is NO product defect established: `shutdown()` refusing to close a database a live worker may be using is deliberate. No recurrence in the nine Windows runs since (all green apart from unrelated, since-fixed test-isolation errors). **Status: root cause of the slow period remains UNEXPLAINED; the test-side failure mode is now guarded.** `AppCase` (tests/p10_common.py) now waits, bounded and by condition, for every controller's tasks and closes the database before the temp folder is deleted, or fails naming the task that never ended (`tests/test_p72_cleanup_isolation.py`, with a negative control). Those tests prove the mechanism on Linux only; the Windows symptom itself cannot be reproduced there. **Recurred once, in a test the net did not cover (CI run 40918820914, commit 0908a6e, which changed only tests and docs):** `test_p42_brain_controller.ChatInteraction.test_a_switch_keeps_the_conversation_memory_and_persona` timed out on a fixed 5 s wait for a chat reply and then hit the same `WinError 32` on `memory.sqlite`. Measured: that run's Windows unit-test step took 464 s against 299-345 s in the three runs before it, so the runner was slow again. `BrainCase` derives from `unittest.TestCase`, not `AppCase`, so it had no safety net; only two classes in the suite build a controller outside `AppCase` (`Rig`, which settles itself, and p42's `Ctl`). The net is now one shared function (`settle_controllers`) used by both bases, and p42's patience limit (`wait`, only ever used inside `assertTrue`) went from 5 s to 30 s. **Still unexplained:** why a task using `memory.sqlite` stalls for 3-5 s or more on some hosted Windows runs (two occurrences, both on slow runs). No product defect has been shown; a real slow-disk delay on a user's PC would be a latency issue, not measured here. **Recurred a third time, in the ORIGINAL P17 test, at normal speed (CI run 40922037937, commit 76eb1cc; Windows unit-test step 331 s, the test body passed, `WinError 32` on `memory.sqlite` at cleanup, safety net active).** That reopened the investigation and found a product-level ordering defect, demonstrated on Linux with a fake model and fake audio: a spoken reply runs on its own helper thread (`jarvis-voice-turn`); the voice worker stops waiting for it after 2 s, and `AppController.shutdown()` did not know about it, so it returned `{'still_running': []}` and closed the assistant's database while that thread was still inside the model. `shutdown()` now reports a running voice reply (the name "voice reply") while that thread lives and leaves the database open; the test safety net waits for it too (`tests/test_p72_cleanup_isolation.py::AVoiceReplyInFlightAtShutdown`, with a negative control that reverts only the controller change). **Not established:** that this defect is what produced the Windows `WinError 32` (the Windows lock itself cannot be reproduced on Linux, and the same failure also happened in tests with no voice reply in flight), and why some hosted Windows runs stall is still unexplained. The intermittent failure occurred in about 3 of ~15 Windows runs, so one green run proves nothing; treat it as fixed only after several consecutive green Windows runs.
- **BOM warning.** `File not found: <U+FEFF>` came from the build script's smoke test (`'' | jarvis.exe setup` in `scripts/build_windows.ps1`), not from the installer check. The bytes in the CI annotation are EF BB BF. Feeding `EF BB BF 0A` to `jarvis setup` on Linux reproduces the line exactly, so the app took a BOM-prefixed answer for a file name. That PowerShell 5.1 adds the BOM when piping was not reproduced here (no PowerShell); it is the only source consistent with the evidence. The first fix (strip U+FEFF) did NOT remove the line in CI run 40804414283: the packaged exe reads piped stdin through the ANSI code page, so the BOM arrives as the three characters `ï»¿` and is echoed back as the same bytes EF BB BF. Feeding the BOM with `PYTHONIOENCODING=cp1252` reproduces the CI bytes on the old code. The wizard now strips either form; whether the next CI log is clean is checked, not assumed.
