# Windows CI (GitHub Actions)

**Status: written and checked locally only.** The workflow `.github/workflows/windows-ci.yml` has never run on GitHub. Its YAML parses and its scripts have Linux tests; the PowerShell in it was not parsed or run by the author (no PowerShell is available in the authoring sandbox). A green run proves only what its steps checked and never means Project Jarvis is finished.

Older, separate workflows exist and are unchanged: `build-windows.yml` (manual or tag; full build **plus a real model download**, real inference and a GUI click test), `model-probe.yml` and `intel-bench.yml` (manual; they download a model). GitHub's run history shows `build-windows` passing at commits up to `bee5873` (2026-10-26), i.e. **before** the selftest worker, the packaging gate and this workflow existed. Nothing since then has run on a Windows runner.

## What `windows-ci` runs

Triggers: pull requests and pushes to `main` that touch `src/`, `tests/`, `packaging/`, `scripts/`, `pyproject.toml`, `config.sample.toml`, `build_installer.bat` or the workflow itself; and manual runs. Documentation-only changes do **not** start it (start it by hand when you want it). A newer push to the same branch cancels the older run. Permissions: `contents: read`. No secrets, no paid API, no schedule, no release, no deployment.

| Job / step | What it does | Needs |
|---|---|---|
| `linux-tests` (Ubuntu, ~5 min) | `pip install -e ".[docs,monitor]"`, the full unit suite with real counts, `check_release_assets.py --source` | nothing else |
| `windows-package` → Build | `scripts\build_windows.ps1 -SkipTorch -SkipTests`: pip installs, llama-cpp-python 0.3.36 wheel, PyInstaller, `check_release_assets.py --dist`, smoke tests of the frozen exe (version, GUI offscreen self-test, `runtime --require`, **`verify_frozen_worker.py`**), VC++ DLL check, Inno Setup installer, checksums, build manifest | network (pip, wheel index), Inno Setup (installed by the job) |
| → Windows unit tests | the full suite on Windows; counts in the run summary; failures make the run red | |
| → Packaged worker gate | `verify_frozen_worker.py --synthetic-model` against the **real** `dist\ProjectJarvis\jarvis.exe` (see below) | |
| → Silent install check | `scripts\clean_install_test.ps1` installs the built installer, launches, uninstalls (keeps data). This runner is not a clean PC | |
| → OPTIONAL real-model test | only on a manual run with the consent value typed (see below) | network, ~1.28 GB |
| → Upload | logs (14 days) through the upload guard; the installer (3 days) only on pushes and manual runs, only when every check passed | |

Every run ends with a summary table that labels each check **PASS / FAIL / NOT RUN / PARTIAL** and lists what it did not verify.

### What the packaged worker gate checks on the real exe
Readiness (`diagnostics`: frozen build, `jarvis.selftest_core` present, nothing missing); `selftest` with no model exits 2 and starts no worker; `selftest-worker` is dispatched and stops at the missing model file; and, with `--synthetic-model`, the real `jarvis.exe selftest` runs on a header-only synthetic `.gguf` generated by the script (never a real model, never committed): the supervisor must start the packaged worker, real llama.cpp must refuse the file (`load_failed`, exit 3), the stages must be recorded in order, and no transient file may remain. **If real llama.cpp crashes on that file, the check fails and says so.** This is dispatch and supervision only; it is not inference.

### Not covered on the real exe
Timeouts, abnormal worker exits (crash codes) and worker start failures on the **real** exe: those are covered only by fake child processes in the Linux tests (`tests/test_p63_*`, `test_p64_*`). Injecting them into the real exe would need a test hook in the production program, which this project does not add.

## Optional real-model test (opt-in, manual only)
Actions → **windows-ci** → *Run workflow* → in `real_inference_consent` type exactly `yes-download-qwen3-1.7b-q4_k_m`. Leave it empty for the normal run (nothing is downloaded).
- Source: `huggingface.co/ggml-org/Qwen3-1.7B-GGUF` (Qwen3-1.7B Q4_K_M), Apache-2.0, about 1.28 GB, downloaded through the app's own consent and SHA-256 path (`models fetch ... --yes`; the typed value is the consent), kept only on the runner (a fresh data folder, deleted at the end, never cached, never uploaded; the upload guard also refuses `.gguf` files).
- It then runs `models verify` and the packaged `jarvis.exe selftest` and judges `selftest.json` with `scripts/ci_check_selftest_report.py`:
  - **BLOCKED** – model could not be downloaded or verified, no model selected, or the runtime is unavailable (reported separately, never as a pass);
  - **FAIL** – load, generation, empty/invalid answer, timeout, crash, or a "pass" whose report contradicts itself;
  - **PASS** – a real model loaded in the worker process, generated a reply and the reply passed the answer check, and report, exit code and files all agree.
- A PASS is one arithmetic answer on one hosted runner. It does not show quality, reasoning, the GUI, voice or any other PC.

## Run it from GitHub
1. Push the branch (this repository's owner decides when). Pull requests and pushes to `main` that touch the paths above start `windows-ci` automatically.
2. Or: GitHub → **Actions** → **windows-ci** → **Run workflow** → pick the branch → (optional consent value) → *Run workflow*. Manual runs need the workflow file to be on the default branch to appear in the list.
3. Open the run → **Summary** for the label table and counts; download `windows-ci-logs` for `build.log`, `unittest-windows.log/.json`, `frozen_worker_gate.log`, `clean_install.log` (and `real_selftest.json` if the optional step ran).

## Cost and limits
Hosted runners only. Repository visibility decides whether runner minutes and artifact storage are free; check Settings and Billing/Usage before relying on it (a Windows build takes tens of minutes). `linux-tests` is the cheap lane; `windows-package` is the expensive one, with a 100-minute job limit and per-step limits. Actions are version-constrained (`@v4`, `@v5`) first-party actions, not pinned to commit hashes.

## Still needs your own Windows PC
Interactive GUI use (looks, scaling, dark mode, focus), microphone/speaker/wake-word voice, computer-control prompts, a genuinely clean-PC install and upgrade, antivirus/SmartScreen behaviour, other CPUs, real timeouts and crashes of the worker, model quality, and final release acceptance. See your Windows acceptance runbook and `docs/WINDOWS_TEST_CHECKLIST.md`.
